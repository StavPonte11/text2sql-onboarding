The Agency — TextToSQL Agent
Production Readiness · Full Implementation Plan
Epics · Stories · Sub-tasks · Tests · Acceptance Criteria · Definition of Done
This document covers the complete implementation path for taking the TextToSQL agent from its current POC state to a production-grade, self-service, regulated platform component. It incorporates the four original problem areas, two capability expansion tracks (geospatial/performance and military Hebrew jargon handling), and all architectural gaps identified during the analysis.

Priority guide
	•	P0 — Blocker. Required before any table goes to production.
	•	P1 — High. Required within first production sprint.
	•	P2 — Medium. Required before general availability.
	•	P3 — Low. Post-GA quality-of-life improvements.


EPIC-1  Metadata Store & Datalake Integration
Replace manual YAML files with a live, enrichable metadata store synced from the datalake API. Includes table registration entities, schema sync, semantic enrichment, and discovery indexing.

EPIC-1 Goal & Scope
All table metadata must be machine-readable, human-enrichable, version-controlled, and indexed for hybrid retrieval. The datalake API is the bootstrap source; a structured enrichment layer on top holds semantic annotations. No agent prompt may reference raw YAML file paths after this epic is complete.

TTS-101  Table Registration Entity & Datalake API Sync
Priority: P0    Estimate: 5 SP
Type
Backend · Data Engineering
Component
Metadata Service (FastAPI + PostgreSQL)
User Story
	•	As a platform engineer, I want every table in the datalake to have a registration record that is auto-populated from the datalake API, so that manual YAML creation is no longer required.
Sub-tasks
	•	Design TableRegistration schema: id, source_id (datalake), schema_name, table_name, columns_json, geo_columns[], time_columns[], status (sandbox/production/degraded), sync_hash, synced_at, created_at, updated_at
	•	Implement datalake API client with retry + circuit breaker (httpx + tenacity)
	•	Write Temporal workflow: SyncTableMetadata — runs every 4h, diffs against stored sync_hash, only writes on change
	•	Implement schema diff logic: detect added columns, removed columns, type changes; set status=degraded on breaking change
	•	Create FastAPI endpoints: GET /metadata/tables, GET /metadata/tables/{id}, POST /metadata/tables/sync (manual trigger)
	•	Add audit log table: every sync writes a diff record (before/after JSON)
Acceptance Criteria
	•	AC1: Temporal sync job runs on schedule and updates records when datalake API schema changes
	•	AC2: Breaking change (column removal or type change) sets table status=degraded and sends an alert
	•	AC3: Manual sync endpoint available for operator use; completes within 30s for up to 500 tables
	•	AC4: Audit log captures full before/after diff per sync event
	•	AC5: No YAML files referenced anywhere in agent runtime after deployment
Tests Required
	•	Unit: datalake API client — mock HTTP, verify retry on 5xx, circuit break after 3 failures
	•	Unit: schema diff logic — added column, removed column, type change, no change — 4 test cases
	•	Integration: Temporal workflow completes against stub datalake API, record updates in PostgreSQL
	•	Integration: breaking change flow → status=degraded → alert emitted
	•	E2E: full sync cycle in staging environment

TTS-103  Hybrid Retrieval Index (Elasticsearch + pgvector)

Type
Backend · ML Infrastructure
Component
Metadata Service + Elasticsearch + pgvector
User Story

Acceptance Criteria

	•	AC2: Tables the user has no permission to see never appear in results
	•	AC3: Retrieval latency p95 < 200ms for up to 1000 indexed tables
	•	AC4: Disambiguation flag is set correctly when two tables from different semantic domains are in the top-2 with close scores
	•	AC5: Index is updated automatically when a table's enrichment is saved or approved
Tests Required

	•	Unit: permission filter — table from forbidden group must not appear regardless of score
	•	Integration: end-to-end retrieval with real Elasticsearch + pgvector in staging
	•	Performance: 100 concurrent discovery requests, measure p50/p95/p99 latency

Definition of Done
Retrieval endpoint deployed, accuracy benchmark passing, latency SLA met, integrated into TextToSQL agent's pre-Composer step.


EPIC-2  Permission Filter & Table Scope Management
Grant users access only to tables they are permitted to see. Implement a three-tier model: hard ACL gate, contextual relevance filter, and user-defined explicit scope.

TTS-201  Hard Permission Gate with Redis Cache
Priority: P0    Estimate: 3 SP
Type
Backend · Security
Component
Permission Service + Redis
User Story
	•	As the platform, I want to enforce the organization's permissions API at query time so that a user can never discover, query, or receive data from a table they are not authorized to access.
Sub-tasks
	•	Implement PermissionClient: wraps internal permissions API, caches results in Redis with 5-minute TTL per user_id
	•	Add permission_groups[] to TableRegistration entity; populated during onboarding
	•	Integrate PermissionClient into discovery endpoint: filter candidate tables by user's permitted groups before returning
	•	Implement cache invalidation: on permission change event (webhook from permissions platform), purge affected user cache keys
	•	Add permission_denied audit log entry whenever a table is filtered from results
Acceptance Criteria
	•	AC1: User with no permissions for group X never sees group X tables in any API response
	•	AC2: Permission cache TTL is configurable; default 5 minutes
	•	AC3: Cache invalidation fires within 10 seconds of a permission change event
	•	AC4: All permission-denied events are audit-logged with user_id, table_id, timestamp
	•	AC5: System degrades gracefully if permissions API is unavailable: use last-known-good cached permissions and alert on-call
Tests Required
	•	Unit: PermissionClient cache hit / miss / TTL expiry
	•	Unit: cache invalidation on webhook event
	•	Security test: user with no group access — verify zero tables returned across all endpoints
	•	Security test: attempt to bypass filter via direct table name injection in query — must be blocked at Composer context-build step
	•	Chaos: permissions API down — verify last-good-cache fallback and alert fires
Definition of Done
Security test cases green, penetration test by one team member confirms no bypass, cache invalidation verified in staging, audit log writing confirmed.

	•	AC5: Table appears in production discovery index within 60 seconds of approval
Tests Required

	•	Integration: publish with 100% pass but one production regression → blocked with correct reason
	•	Integration: platform override → table publishes, override recorded in audit log

TTS-402  Performance Safeguards — Cost Limits & Circuit Breaker
Priority: P1    Estimate: 4 SP
Type
Backend · Infrastructure
Component
TextToSQL agent — Refiner + Trino
User Story

Sub-tasks

Acceptance Criteria
	•	AC1: Refiner never exceeds 4 iterations regardless of error type
	•	AC2: Queries exceeding wall-clock timeout are cancelled at Trino level, not just abandoned
	•	AC3: Cost estimate warning is shown to the user before executing large scans
	•	AC4: All Refiner metrics (iterations, execution time, rows scanned) are visible in Langfuse
	•	AC5: Trino resource group correctly tags and throttles agent queries per user
Tests Required
	•	Unit: Refiner — force 4 consecutive failures, verify exit and structured error
	•	Integration: timeout simulation — mock Trino delay > 120s, verify cancellation
	•	Integration: large scan — EXPLAIN returns >10GB estimate, verify warning emitted before execution
	•	Load: 10 concurrent agent invocations, verify Trino resource group throttles correctly
Definition of Done
Circuit breaker tested in staging, Trino resource group configuration deployed, cost metrics visible in Langfuse dashboard.

EPIC-5  Military Hebrew Jargon & Glossary Integration
Handle the organization's domain-specific Hebrew acronyms and terminology at query understanding time. Split into quick wins (low effort) and advanced implementation (long-term).

Context & Strategy
The jargon dictionary is a JSON file of acronym → full term + optional definition mappings in Military Hebrew. The problem has two distinct failure modes: (1) the model does not expand an acronym and generates SQL with a term that does not exist in any column value; (2) the model misinterprets an acronym that exists as a common word. The implementation is staged from zero-effort injection to full semantic retrieval.

TTS-501  Phase 1 — Static Jargon Injection at Composer Context (Low Effort)
Priority: P1    Estimate: 2 SP
Type
AI Engineering — Prompt Engineering
Component
TextToSQL agent — Composer
User Story
	•	As the platform, I want to inject a compact representation of the jargon dictionary into the Composer's system prompt so that the model can expand acronyms before generating SQL, without any infrastructure changes.
Sub-tasks
	•	Parse jargon JSON into a compact text block format: '(אמ"ן) → אגף המודיעין — Military Intelligence Directorate' one entry per line
	•	Segment dictionary by category if available; otherwise use full dictionary if token count < 800 tokens
	•	Inject jargon block into Composer system prompt under a dedicated 'Domain Glossary' section; instruct model to always check this section before referencing any value in a WHERE clause
	•	Add jargon expansion step instruction: 'Before generating SQL, list all acronyms in the user query and their expansions from the glossary. If an acronym is not in the glossary, use it as-is and note it is unknown.'
	•	Measure token overhead; if dictionary exceeds 800 tokens, implement top-50 most common terms selection heuristic
Acceptance Criteria
	•	AC1: Queries containing known acronyms produce SQL that uses the expanded form in WHERE clauses
	•	AC2: Token overhead of jargon injection does not exceed 1000 tokens in the Composer prompt
	•	AC3: Jargon block is sourced from the JSON file at agent startup, not hardcoded
	•	AC4: Unknown acronyms are passed through unchanged with a note in the agent's reasoning trace
Tests Required
	•	Prompt test: 10 queries with known acronyms — verify correct expansion in generated SQL
	•	Prompt test: 5 queries with unknown acronyms — verify pass-through without hallucination
	•	Token count test: full dictionary injection verified <1000 tokens with current model tokenizer
Definition of Done
Jargon injection live in staging Composer, 10-query test set passes, token overhead measured and documented.

TTS-503  Phase 2 — Jargon Knowledge Base with Semantic Retrieval (Advanced)
Priority: P3    Estimate: 8 SP
Type
AI Engineering · ML Infrastructure
Component
Metadata Service + Elasticsearch + pgvector
User Story
	•	As the platform, I want the jargon dictionary indexed for semantic retrieval so that contextually relevant terms are dynamically injected rather than the full dictionary, and so that new terms can be added without redeploying the agent.

	•	Index jargon JSON into Elasticsearch: each entry is a document with acronym, full_term, definition, category, aliases[], example_usage

TTS-603  Query Result Validation & Sanity Checks

Type

	•	AC3: Sanity warnings are always in the user's language (Hebrew/English)
	•	AC4: Warnings do not block result delivery — user always gets the data plus the warning
Tests Required
	•	Unit: ResultValidator — zero rows, large result, correct result — 3 test cases
	•	Integration: zero-row recovery — verify relaxed query runs and suggestion generated
	•	UI: warning field rendered correctly in Friday portal chat
Definition of Done
ResultValidator in LangGraph graph, zero-row recovery tested with real Trino queries in staging, warnings surfaced in UI.

Global Definition of Done (applies to all stories)

Engineering standards
	•	Code reviewed by at least one other engineer before merge
	•	All unit and integration tests pass in CI (zero failures, zero skips without justification)
	•	No new Pydantic v1 patterns introduced; all models use Pydantic v2 field validators
	•	Type hints on all new Python functions and return values
	•	FastAPI endpoints have OpenAPI documentation with response schemas
	•	No hard-coded secrets, API keys, or connection strings — all via environment variables
	•	Temporal workflows have explicit retry policies and timeout configurations
	•	All async code uses structured concurrency (no bare asyncio.create_task without tracking)

Observability standards
	•	All new agent nodes emit a Langfuse span with input, output, latency, and model version
	•	All FastAPI endpoints emit structured logs (JSON) with request_id, user_id, duration_ms
	•	Errors are logged with full stack trace and a user-facing message that does not leak internals
	•	New metrics added to existing Grafana dashboard (or a new panel created if no existing dashboard)

Bilingual & accessibility standards
	•	All user-facing text is bilingual: Hebrew (RTL) and English (LTR)
	•	RTL layout tested on Chrome and Firefox on latest stable versions
	•	All new form inputs have aria-label attributes
	•	Agent responses in Hebrew use correct grammatical gender agreement where applicable
